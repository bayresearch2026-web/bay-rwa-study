RWA 지갑의 분류와 통제 구조

외부지갑 · 서비스 내 지갑 · 사용자 통제형 · 사업자 통제형 · 수탁 — 핵심 개념 정리

0. 기본 전제

  • 토큰은 지갑 안에 있는 게 아니라 블록체인에 기록됨
  • 지갑 = 블록체인 계정에 접근하고 거래를 승인하는 도구

핵심 질문은 두 가지임.

질문 1

누가 지갑을 제공하나?

질문 2

1. 사용자 관점의 지갑 분류

1-1. A. 외부지갑 연결형

사용자가 이미 가진 지갑을 서비스에 연결하는 구조임.

예: MetaMask, 기관용 지갑, 수탁기관 지갑

핵심 분류 기준

“서비스 밖에서 마련한 지갑인가?”

연결 기술

WalletConnect / 연결 SDK 등

장점과 단점

장점

  • 기존 지갑 계속 사용 가능
  • 여러 온체인 서비스와 연결하기 쉬움

단점

  • 지갑 설치·키 관리·가스비 등 진입장벽
  • RWA의 경우 새 주소마다 KYC/화이트리스트 등록 필요 가능

1-2. B. 서비스 내 지갑 제공형

서비스 가입 과정에서 지갑을 함께 만들어주는 구조임.

  • 이메일/소셜 로그인 등으로 사용 가능
  • 지갑 설치 불필요
  • KYC + 지갑 생성 + 승인주소 등록을 한 흐름으로 묶기 쉬움
  • 가스비 대납 등으로 일반 금융앱 같은 UX 가능
서비스 내 지갑 제공형은 다시 누가 실제 서명 권한을 갖는가를 기준으로 나눌 수 있음.

1-3. B-1. 사용자 통제형

  • 서비스가 지갑은 만들어줌
  • 최종 서명 권한은 사용자에게 있음
  • 플랫폼은 사용자 허용 없이 자산 이동 불가

일부 권한 위임 가능

  • 금액 제한
  • 기간 제한
  • 자산 제한
  • 대상 제한

장점과 단점

장점

  • 쉬운 온보딩 + 사용자 통제권 유지

단점

  • 사용자 승인 없으면 업무 중단 가능
  • 상속·분쟁·법적 동결 대응이 어려울 수 있음

1-4. B-2. 사업자 통제형

  • 서비스가 지갑 제공
  • 사업자 또는 외부 수탁기관이 서명 권한 관리
  • 사용자는 “거래 요청”만 함
  • 실제 온체인 거래는 사업자/수탁기관이 실행

장점과 단점

장점

  • 키 관리 불필요
  • 계정 복구 쉬움
  • 상속·분쟁·동결 대응 가능

단점

  • 출금·이전이 사업자 절차에 의존
  • 사업자 중단/파산 시 반환 구조가 중요

2. 절대 헷갈리면 안 되는 것

외부지갑 vs 서비스 내 지갑

지갑을 어디서 마련했는가의 문제

사용자 통제형 vs 사업자 통제형

누가 실제 서명 권한을 갖는가의 문제

2-1. 수탁

누가 법적으로 고객자산을 맡고 반환 책임을 지는가의 문제

서명 권한과 수탁 지위는 같은 개념이 아님.

3. 이 장의 최종 결론

  • 화면에 보이는 지갑 형태만 봐서는 실제 자산 통제 구조를 알 수 없음
  • 외부지갑도 외부 수탁기관이 관리할 수 있음
  • 사업자 통제형도 사업자가 직접 서명할 수도, 외부 수탁기관에 맡길 수도 있음
화면에 보이는 지갑 형태
≠
실제 자산 통제 구조

그래서 다음 단계에서는:

“기업이 고객자산과 기업자산을 실제로 어떻게 통제하는가”

를 따로 봐야 함.

APPENDIX 2

Kresus

화이트라벨 지갑과 RWA 토큰화 인프라

Kresus는 무엇인가

Kresus는 아주 쉽게 말하면 “회사가 자기 이름으로 디지털 지갑 서비스를 만들 수 있게 해주는 지갑 제작·운영 도구 회사”임.

예를 들어 한화투자증권이 직접 처음부터 지갑 앱을 개발하려면 굉장히 많은 기술이 필요함. 그런데 Kresus를 쓰면 Kresus가 만들어둔 지갑 기술을 가져다가 ‘한화투자증권 지갑’처럼 꾸며서 제공할 수 있음.

1. 화이트라벨 지갑이 무엇인가

화이트라벨은 쉽게 말하면:

기술은 Kresus가 만들고, 겉에는 고객 회사 브랜드를 붙이는 것

임.

예를 들어 Kresus가 기본 지갑 시스템을 만들어놨다고 가정.

  • Kresus 기술
  • 한화투자증권 로고
  • 한화투자증권 디자인
  • 한화투자증권 고객 대상 서비스

이렇게 만들면 고객 입장에서는 “한화 지갑”을 쓰는 것처럼 보이지만, 뒤에서는 Kresus 기술이 돌아갈 수 있음.

2. 지갑을 제공하는 방식도 여러 개임

본문에서 세 가지가 나왔음.

① 임베디드 지갑

기존 앱 안에 지갑을 넣는 방식임.

예를 들어 한화투자증권 앱에:

주식 / 채권 / RWA / 디지털자산 지갑

이런 메뉴를 추가하는 방식.

사용자는 별도 앱을 설치할 필요가 없음.

② 웹 포털

웹사이트에 로그인해서 지갑을 사용하는 방식임.

예:

wallet.hanwha.com

같은 사이트에 들어가서 자산을 확인하고 전송하는 구조임.

③ 독립 앱

아예 별도의 지갑 앱을 만드는 방식임.

예:

“Hanwha Digital Wallet”

이라는 앱을 따로 출시하는 것임.

3. 누가 키를 통제할지도 선택할 수 있음

이 부분이 더 중요함.

Kresus는 지갑 모양만 만들어주는 것이 아니라 누가 실제 자산을 통제할지도 여러 방식으로 설계할 수 있음.

사용자 통제형

고객이 자기 키를 통제하는 구조임.

사용자가 비밀번호나 인증수단을 가지고 있고, 사용자 승인 없이는 자산을 움직일 수 없음.

쉽게 말하면 “내 지갑, 내 통제”에 가까움.

사업자 통제형

서비스 회사가 키 또는 승인 권한을 통제하는 구조임.

한화투자증권 시스템이 고객 대신 거래를 서명하거나 승인하는 구조임.

은행 앱이 고객 대신 내부적으로 자금을 처리하는 것과 조금 비슷한 느낌으로 이해할 수 있음.

혼합형

둘을 섞는 구조임.

고객 인증 + 회사 승인

둘 다 있어야 거래가 되는 방식임.

따라서 Kresus는 단순히 “지갑 앱 하나 만들어주는 회사”가 아니라, 기업이 원하는 방식으로 지갑의 껍데기와 통제 구조를 조립할 수 있게 해주는 인프라라고 볼 수 있음.

4. 그런데 왜 RWA 얘기가 같이 나오는가

Kresus는 지갑만 하는 것이 아니라 Kite라는 RWA 토큰화 플랫폼도 같이 제공함.

Kresus

지갑

Kite

실제 자산을 블록체인 토큰으로 만들고 관리하는 시스템

이라고 이해할 수 있음.

예를 들어 빌딩 지분이나 채권을 토큰화한다고 가정.

Kite는:

  • 토큰 발행
  • 토큰 관리
  • 누가 보유하는지 관리
  • 결제
  • 자산 이전

같은 일을 지원할 수 있음.

그리고 Kresus 지갑은 그 토큰을 고객이 보고, 들고, 거래하는 접점이 됨.

따라서 둘을 붙이면:

RWA 발행
↓
지갑 보관
↓
거래
↓
결제

까지 한 묶음으로 제공하려는 구조가 됨.

5. 스테이블코인 결제도 왜 붙어 있는가

RWA를 사고팔 때 결제수단이 필요하기 때문임.

예를 들어 토큰화된 미국채를 산다고 가정하면:

고객 USDC 지급
↓
RWA 토큰 수령

같은 구조를 만들 수 있음.

따라서 Kresus는 지갑만 만드는 것이 아니라

지갑 + RWA 토큰화 + 스테이블코인 결제

를 하나의 기업용 패키지처럼 제공하려는 구조임.

6. 한화투자증권 사례는 그래서 의미가 있음

한화투자증권이 Kresus와 협력했다는 것은 단순히

“지갑 앱 하나 만들어주세요”

수준일 수도 있지만, 협약 범위가

  • 디지털 지갑
  • 토큰화
  • 블록체인 기술

까지 포함되어 있으므로,

좀 더 크게 보면:

증권사가 미래의 토큰화 증권/RWA 서비스를 만들기 위해 외부 지갑·토큰화 기술회사를 파트너로 붙이는 구조

라고 이해할 수 있음.

이것이 이 글에서 Kresus 사례를 든 이유임.

7. 그런데 마지막 문단은 왜 경고를 하는가

이 부분이 중요함.

Kresus가 홈페이지에서:

“우리는 이런 기능을 제공합니다.”

라고 설명한다고 해서 모든 세부사항을 알 수 있는 것은 아님.

기업이 실제 도입하려면 추가 확인이 필요함.

  • 키를 실제로 누가 보관하는가?
  • 고객이 키를 잃으면 복구 가능한가?
  • Kresus가 망하면 지갑을 다른 업체로 옮길 수 있는가?
  • 어떤 블록체인을 정확히 지원하는가?
  • 보안 인증은 어디까지 받았는가?
  • 고객 정보가 어디 저장되는가?

이런 내용은 홈페이지 홍보자료만으로는 부족할 수 있다는 의미임.

따라서 본문에서 말하는 “개별 실사”는:

기업이 실제 계약하기 전에 기술·법률·보안 구조를 직접 검증해야 함

이라는 의미임.

전체를 한 장면으로 생각하면

한화투자증권이 앞으로 토큰화된 채권 상품을 만든다고 가정.

Kite
채권을 토큰화
↓
Kresus
고객에게 “한화 디지털 지갑” 제공
↓
스테이블코인
고객이 토큰을 사고팔 때 결제

따라서 고객 입장에서는:

한화 앱 로그인
↓
토큰화 채권 구매
↓
내 지갑에 보유
↓
나중에 매도 또는 환매

같은 경험이 가능해지는 구조임.

한 줄 요약: Kresus는 금융회사나 기업이 자기 브랜드로 디지털 지갑을 만들고, 그 지갑을 RWA 토큰화와 스테이블코인 결제까지 연결할 수 있게 해주는 B2B 지갑 인프라 회사임.

APPENDIX 3

Privy

조립형 지갑 인프라 · Policy Engine · Kresus 비교

1. Privy를 이해하기 전에 모르는 단어부터 잡고가자

1-1. “저수준 API”란?

여기서 저수준은 “수준이 낮다”는 뜻이 아니라, 개발자가 더 세세한 기능까지 직접 만질 수 있다는 뜻임.

예를 들어 자동차로 비유하면:

  • 높은 수준의 API = “목적지만 입력하면 알아서 운전”
  • 저수준 API = “가속, 브레이크, 핸들 조작까지 직접 설정 가능”

Privy에서는 개발자가 단순히

“지갑 하나 만들어줘”

만 요청하는 게 아니라,

  • 누가 서명할지
  • 언제 자동 서명할지
  • 어떤 거래를 허용할지
  • 얼마까지 송금할지
  • 몇 명이 승인해야 할지

같은 것을 코드로 세밀하게 설정할 수 있음. Privy도 정책, 서명자, 거래 제어 기능을 개발자가 직접 구성할 수 있도록 제공한다고 설명함. Privy

Privy = 완제품보다 개발 부품에 가까운 이유가 여기 있음.

1-2. 정책 엔진(Policy Engine)이란?

“이 지갑이 해도 되는 행동과 하면 안 되는 행동을 검사하는 규칙 검사기”

예를 들어 회사 지갑에 100억 원이 있다고 가정.

회사가 다음 규칙을 넣을 수 있음.

  • 하루 최대 1억 원까지만 송금
  • 등록된 주소로만 송금
  • 특정 스마트컨트랙트만 사용
  • 5천만 원 이상이면 2명 승인 필요
  • 특정 거래에는 MFA 필요

직원이 거래를 요청하면:

거래 요청
↓
Policy Engine이 규칙 검사
↓
통과하면 서명
↓
실패하면 거래 차단

같은 구조임.

Privy는 실제로 recipient allowlist, contract allowlist, 최대 이전 금액, calldata 제한, MFA, 복수 승인 등을 정책으로 설정할 수 있다고 공개하고 있음. Privy

회계감사 식으로 비유하면 지갑 안에 자동화된 내부통제를 넣는 것에 가까움.

1-3. “문서화 수준이 높다”는 게 어떤 의미?

여기서 문서는 일반 사용자용 설명서가 아니라 주로 개발자 문서(Developer Documentation)를 의미함.

예를 들어 Privy가 그냥 홈페이지에서

“우리 지갑은 안전합니다!”

라고만 하면 실제 구조를 알기 어려움.

문서화가 잘되어 있다는 건:

  • API를 어떻게 사용하는지
  • 키가 어떻게 관리되는지
  • 어떤 custody 구조가 가능한지

  • 어떤 권한 모델이 있는지
  • 어떤 체인을 지원하는지
  • 실패했을 때 어떤 응답이 오는지
  • 어떤 보안 기능이 있는지

같은 것들이 개발자가 실제 구현할 수 있을 정도로 상세하게 공개돼 있다는 뜻임.

Privy는 embedded wallet 구조, key-management 방식, transaction controls, policy engine, approval 구조, gas sponsorship 등을 비교적 구체적으로 공개하고 있음. Privy

그러니까:

“우리 제품은 이런 기능이 있습니다”

에서 끝나는 게 아니라

“이 기능이 실제로 이런 방식으로 작동하고, 개발자는 이렇게 사용할 수 있습니다”

까지 공개되어 있다는 의미임.

1-4. 그런데 문서화가 잘 되어 있으면 왜 “사전 검증”에 유리?

기업 입장에서는 제품을 계약하기 전에 “이 제품을 우리 회사에 정말 써도 되는지” 검토해야 함.

예를 들어 금융회사가 Privy를 도입한다고 가정.

보안팀

개발팀

리스크팀

컴플라이언스팀

고객 통제형과 회사 통제형을 구분할 수 있나?

같은 내용을 확인해야 함.

문서가 상세하면 계약하거나 실제 시스템을 구축하기 전에도 상당 부분을 확인할 수 있음.

반대로 문서가 거의 없다면:

영업팀에 문의

미팅

↓
기술팀 질문

추가 확인

을 해야 겨우 알 수 있음.

그래서 본문의

“문서화 수준이 높다는 점은 사전 검증에 유리하다”

는 말은

돈 들여 도입하기 전에 기술 구조와 기능을 미리 검토하기 쉽다

는 의미임.

중학생 수준으로 한마디로 하면: 제품 설명서가 자세할수록 사기 전에 제품 내부를 더 많이 확인할 수 있음.

1-5. 그러면 RWA 기능을 Privy가 안 해준다면 Kresus는?

여기가 제일 중요한 질문임.

Kresus는 Privy보다 RWA 쪽으로 한 단계 더 들어가 있음.

왜냐하면 Kresus에는 지갑뿐 아니라 KITE라는 토큰화 플랫폼이 있기 때문임.

현재 Kresus는 KITE를 토큰화 투자상품을 발행부터 결제까지 지원하는 인프라로 설명하고 있고, compliance rules와 transfer restrictions를 자산에 적용하는 기능도 제시하고 있음. Kresus Labs

Privy

주로:

“지갑을 어떻게 만들고 안전하게 움직일 것인가?”

를 해결함.

예:

  • 로그인
  • 지갑 생성
  • 키 관리
  • 거래 서명
  • 승인 정책
  • 가스비 대납

그런데:

이 투자자가 전문투자자인가?
이 토큰을 B에게 넘겨도 되는가?
법적 소유자 명부가 어떻게 바뀌는가?

같은 RWA 상품 레이어는 별도 시스템과 연결해야 함.

“지갑도 주고, RWA를 발행·관리하는 시스템도 같이 제공할게.”

조금 더 완성차 패키지에 가까움.

다만 자동차를 줬다고 해서

운전면허, 도로교통법, 자동차 등록

그래서 이 글에서 Privy와 Kresus를 비교할 때 가장 핵심적인 차이는:

Privy는 Wallet Infrastructure 중심이고, Kresus는 Wallet + Tokenization Infrastructure까지 범위가 더 넓음.

이라고 잡으면 됨.

2. Privy의 기능과 구조

Privy는 Kresus보다 “완성품”이 아니라 “부품 세트”에 가까운 지갑 인프라라고 보면 됨.

2-1. Privy는 뭐 하는 회사냐

아주 쉽게 말하면:

앱이나 웹서비스 안에 로그인 + 지갑 기능을 심을 수 있게 해주는 개발 도구

임.

예를 들어 어떤 RWA 스타트업이 앱을 만들었다고 가정.

사용자가 앱에 들어와서:

  • 이메일이나 소셜 계정으로 로그인
  • 자동으로 지갑 생성
  • RWA 토큰 구매
  • 자산 확인
  • 거래 승인

까지 하게 만들고 싶을 수 있음.

Privy는 이런 기능을 앱 안에 자연스럽게 넣을 수 있게 해주는 인프라임.

2-2. Kresus랑 뭐가 다르냐

여기가 가장 중요함.

Kresus는 상대적으로:

“지갑 완성품을 가져다가 우리 브랜드로 쓰는 방식”

에 가까움.

반면 Privy는:

“지갑을 만드는 데 필요한 부품과 API를 줄 테니, 화면과 사용자 경험은 너희가 직접 만들어라”

에 가까움.

Kresus

완성된 레고 모델을 받아서 로고만 바꾸는 느낌

Privy

레고 블록 세트를 받아서 원하는 모양으로 직접 조립하는 느낌

그래서 본문에서 Privy를 “조립형”이라고 표현한 것임.

2-3. 사용자 지갑도 만들고 기업 지갑도 만들 수 있음

Privy를 이용한다고 해서 무조건 개인용 지갑만 만드는 것은 아님.

사용자 통제형

사용자에게 지갑을 만들어주되, 실제 통제권은 사용자에게 남기는 구조임.

예:

사용자가 이메일로 로그인
↓
앱 안에서 자동으로 지갑 생성
↓
거래할 때 사용자가 직접 승인

사용자는 MetaMask 같은 별도 앱을 설치하지 않아도 됨.

기업 통제형

기업이 여러 개의 지갑을 만들어서 직접 관리할 수도 있음.

예를 들어 RWA 회사가:

  • 고객 입금용 지갑
  • 정산용 지갑
  • Treasury 지갑
  • 운영용 지갑

을 여러 개 만들어 관리할 수 있음.

권한을 나눌 수도 있음

예를 들어 100억 원짜리 기업 지갑이 있다고 가정.

아무 직원이나 돈을 보내면 안 됨.

  • 직원 A: 거래 요청 가능
  • 팀장 B: 승인 가능
  • CFO C: 10억 이상 거래만 추가 승인

같이 권한을 설정할 수 있음.

즉 Privy는 단순히 “지갑 주소 만들어주는 서비스”가 아니라, 누가 어떤 거래를 할 수 있는지까지 프로그래밍할 수 있는 지갑 인프라에 가까움.

2-4. TEE와 키 분할은 뭐냐

여기부터 기술적인 부분임.

지갑에서 가장 중요한 건 Private Key, 즉 자산을 움직일 수 있는 비밀키임.

Privy는 이 키를 그냥 서버에 통째로 저장하지 않고, 보안을 높이기 위해 여러 기술을 사용함.

TEE

TEE는 Trusted Execution Environment, 신뢰 실행 환경임.

쉽게 말하면:

컴퓨터 안에 만들어 놓은 잠긴 금고 같은 공간

이라고 생각하면 됨.

일반 프로그램이나 서버 관리자가 마음대로 내부를 볼 수 없도록 격리된 환경에서 중요한 작업을 수행함.

예를 들어:

“이 거래에 서명해”

라는 요청이 들어오면 중요한 키 연산을 이 보호된 공간 안에서 처리하는 방식임.

키 분할

그리고 키를 한 곳에 통째로 두지 않는 구조도 사용함.

쉽게 말하면 보물상자 열쇠를 하나 만들어서 서버에 넣어두는 게 아니라:

열쇠 조각 A + 열쇠 조각 B

같이 나눠놓는 느낌임.

그래서 한 부분이 탈취돼도 바로 전체 자산을 움직이지 못하도록 방어하는 구조임.

“Private Key 하나가 어딘가에 그대로 놓여 있는 위험을 줄임.”

2-5. 세션 서명자는 뭐냐

이건 사용자 경험을 좋게 만드는 기능이라고 생각하면 됨.

블록체인을 직접 써보면 거래할 때마다:

승인하시겠습니까?
서명하시겠습니까?

가 계속 뜰 수 있음.

그런데 게임이나 금융서비스에서 매번 클릭하라고 하면 너무 불편함.

그래서 일정 조건 안에서는 미리 권한을 받은 프로그램이 대신 거래에 서명하게 만들 수 있음.

예를 들어:

앞으로 1시간 동안
이 특정 컨트랙트에서
최대 100 USDC까지만
자동으로 거래 허용

같은 방식임.

이렇게 제한된 권한을 가진 임시 서명 주체를 session signer라고 생각하면 이해하기 쉬움.

2-6. Policy Engine은 굉장히 중요함

Privy가 단순 지갑 생성 도구를 넘어 기업용으로 쓸 만한 이유 중 하나임.

Policy Engine = “이 지갑이 무엇을 할 수 있는지 규칙을 정하는 시스템”

이라고 보면 됨.

예를 들어 기업이 다음 규칙을 넣을 수 있음.

허용 컨트랙트

이 지갑은 Aave와 USDC 컨트랙트만 사용할 수 있음.

이상한 스마트컨트랙트에 연결해서 자산을 빼가는 사고를 줄이는 구조임.

허용 수취인

돈은 등록된 회사 지갑 10개에만 보낼 수 있음.

갑자기 해커 주소로 100억 원이 전송되는 걸 막을 수 있음.

최대 이전 금액

하루 최대 10만 USDC까지만 송금 가능.

Contract Call Data 제한

조금 더 고급 기능임.

특정 스마트컨트랙트를 사용하더라도 허용된 행동만 실행

하게 만들 수 있다는 뜻임.

즉:

“Aave는 써도 됨”

뿐 아니라

“Aave에서 이 행동만 해도 됨”

까지 제한할 수 있다는 의미임.

2-7. 다중 인증과 복수 승인도 가능

예를 들어 직원 A가 100만 USDC를 보내려고 한다고 가정.

Privy를 통해:

직원 A 거래 요청
↓
팀장 B 승인
↓
CFO C 승인
↓
거래 실행

같은 구조를 만들 수 있음.

즉 기업 내부통제를 블록체인 지갑에 집어넣을 수 있는 구조임.

회계감사 관점으로 생각하면 이해하기 쉬움.

거래 요청자와 승인자를 분리하는 내부통제를 지갑 레벨에서 구현하는 것이라고 보면 됨.

2-8. 가스비 대납은 뭐냐

블록체인에서 거래하면 보통 ETH 같은 네이티브 토큰으로 gas fee를 내야 함.

RWA 서비스를 처음 쓰는 고객한테:

“토큰화 국채를 사시려면 먼저 ETH를 거래소에서 사고 지갑으로 보내세요.”

라고 하면 UX가 끔찍해짐.

Privy를 사용하면 기업이 대신 gas fee를 낼 수 있음.

사용자는 그냥:

“구매”

버튼만 누르고,

뒤에서는 기업이 가스비를 처리하는 구조임.

그래서 일반 금융 앱처럼 UX를 만들기가 쉬워짐.

2-9. 그런데 Privy가 RWA 전체를 만들어주는 건 아님

본문 마지막 문장이 핵심임.

Privy는 지갑 쪽은 상당히 잘 만들어주지만,

“이 사람이 이 RWA를 사도 되는 사람인가?”

까지 판단해주는 시스템은 아니라는 의미임.

RWA에서는 별도의 문제들이 있음.

투자자 적격성

예를 들어 어떤 사모상품은:

전문투자자만 구매 가능

할 수 있음.

Privy가 지갑을 만들어줬다고 이 사람이 전문투자자인지 자동으로 판단되는 것은 아님.

명의개서

예를 들어 토큰화 채권을 A가 B에게 넘겼다고 가정.

블록체인상:

A 지갑 → B 지갑

으로 토큰이 이동했다고 해서,

법률상 채권자 명부도 자동으로:

A → B

로 바뀌는 것은 아닐 수 있음.

따라서 공식 투자자 명부/명의개서 시스템과 연결해야 할 수 있음.

상품별 이전 제한

예를 들어:

미국 투자자에게만 이전 가능
KYC 완료 지갑에만 이전 가능
1년 동안 양도 금지
전문투자자끼리만 이전 가능

같은 규칙이 있을 수 있음.

이건 Privy 지갑 자체가 해결하는 게 아니라,

RWA 토큰의 스마트컨트랙트 + KYC 시스템 + 투자자 registry

같은 다른 시스템과 연결해서 만들어야 함.

APPENDIX 3-A · PRIVY

TSS-MPC vs Multisig

키 지분 · 독립 키 · 2/3 구조 · 서명 방식 · 체인 호환성

1. 핵심 차이

핵심 차이는 “키를 여러 조각으로 나누느냐” vs “서로 다른 여러 키가 각각 서명하느냐”임.

구분 TSS-MPC 멀티시그
기본 구조 하나의 키를 여러 지분으로 나눔 여러 개의 독립된 키를 사용
서명 결과 외부에서는 보통 하나의 일반 서명처럼 보임 여러 서명이 필요하다는 구조가 명시됨
예시 3개 키 지분 중 2개가 협력해 하나의 서명 생성 A, B, C라는 3개 키 중 2개가 각각 서명
구현 위치 주로 오프체인 암호기술 주로 스마트컨트랙트/체인 로직
체인 호환성 일반 지갑처럼 보이므로 비교적 넓음 체인이 멀티시그 구조를 지원해야 함

2. 각각의 구조

2-1. TSS-MPC

아까 Dynamic 사례처럼:

  • 사용자 기기: 키 지분 A
  • 서버: 키 지분 B
  • 복구용: 키 지분 C

가 있다고 가정.

2/3 TSS-MPC라면 이 중 2개가 협력해서 하나의 정상적인 블록체인 서명을 생성함.

중요한 건 A나 B가 각각 완전한 private key가 아니라는 점임.

키 지분 A
+
키 지분 B
↓
암호학적으로 협력
↓
최종 서명 1개 생성

체인 입장에서는 그냥:

“이 지갑의 정상적인 서명 하나가 들어왔네.”

처럼 보일 수 있음.

2-2. 멀티시그

멀티시그에서는 애초에 완전한 private key가 여러 개 있음.

예를 들어 회사에:

  • CFO 개인키 A
  • 팀장 개인키 B
  • 대표 개인키 C

가 있고,

2-of-3 멀티시그라면:

A, B, C 중 아무 2명이 각자의 키로 서명해야 거래 실행

되는 구조임.

A의 독립 서명
+
B의 독립 서명
↓
거래 승인

3. 금고 비유로 이해하기

TSS-MPC

금고 열쇠 하나를 세 조각으로 잘라놓은 것과 비슷함.

조각 3개 중 2개를 이용해
하나의 열쇠 역할을 수행

각 조각 하나만으로는 열쇠가 아님.

멀티시그

금고 자체가:

서로 다른 열쇠 3개 중 2개를 꽂아야 열리는 금고

인 구조임.

각 사람이 가지고 있는 건 전부 독립적인 완전한 열쇠임.

4. 둘 다 2/3인데 왜 다른가

둘 다 2/3이라는 표현을 쓸 수 있음.

하지만 의미가 다름.

TSS-MPC 2/3

키 지분 3개 중 2개가 협력해 하나의 서명 생성

Multisig 2/3

독립된 키 3개 중 2개가 각각 별도로 서명

이 차이가 핵심임.

5. 기업에서는 왜 TSS-MPC를 많이 쓰는가

TSS-MPC는 결과적으로 일반적인 단일 서명처럼 처리될 수 있어서 여러 블록체인에 적용하기 편한 경우가 많음.

반면 멀티시그는 Safe 같은 스마트컨트랙트 지갑을 만들어서:

“이 거래는 3명 중 2명이 승인해야 한다.”

라는 규칙 자체를 온체인에 구현하는 경우가 많음.

5-1. 아주 단순화하면

TSS-MPC = 하나의 private key 권한을 암호학적으로 쪼개서 관리
Multisig = 여러 private key의 승인을 모아서 거래

아까 Dynamic의 2/2, 2/3은 멀티시그가 아니라 TSS-MPC에서 키 지분이 몇 개 필요하냐를 말한 것임.
